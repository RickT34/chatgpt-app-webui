# 浏览器启动开销调查与优化（2026-10-14）

宿主已经常驻，但浏览器每次打开仍会初始化原版界面。此次减少了重复工具校验、配置初始化及陈旧启动快照造成的工作。完整页面复测有小幅改善，**还不能宣称达到“服务器启动一次，任何浏览器都立即进入”**。

## 已确认的原因

- **大文件重复校验。** 原版 Chrome 插件运行时会比较已安装工具与包内工具，使用 `readFile` 读取整个文件再计算 SHA-256。采样中一次初始化读取了 4 个文件、共 643,050,640 字节；后续页面初始化仍会进入该验证路径。这既消耗 CPU，也会分配大块 Buffer。
- **配置缓存写不进去。** 原 Statsig SDK 需要写入约 540 万字符，超过本机 localStorage 配额；此前每次页面捕获到 5 次 `QuotaExceededError`。
- **已有配置仍被重新初始化。** 原版已有宿主设备身份服务：前端调用 `statsig.getStableId`，再用 `StableID.setOverride`。同一宿主上的新浏览器可以拥有完全相同的配置身份，之前没有利用宿主已保存的完整配置。
- **启动快照滞后。** 桥接只在宿主启动时读取快照；原版 preload 的侧栏 getter 还会在隐藏窗口内永久缓存第一次结果。单纯重新调用这个 getter 无法拿到当前状态。
- **网页误用桌面上报通道。** Electron Sentry SDK 在网页反复请求 `sentry-ipc://`，被 CSP 拒绝，产生大量失败信息。
- **剩余界面工作较重。** 真实页面仍加载并执行约 11.4 MB 的 app-initial 和 8.2 MB 的 app-shared 源代码，以及后续路由、语言和功能模块；还有项目、插件、会话及 Git 查询。宿主服务握手快不等于完整首屏快。

这些判断来自本机原包源码、真实页面和进程采样；没有用域名连通性或某个配置请求成功来推断启动原因。

## 当前实现

### 工具文件校验

在私有 App 副本中替换原运行时的唯一文件摘要函数，调用者仍按原逻辑决定验证哪些文件，以及是否修复安装。

首次使用分块读取计算摘要；后续每次检查 dev、inode、mode、size、mtimeNs 和 ctimeNs，未变化时复用摘要。读取前后核对打开文件的元数据；失败或发生变化的读取不进入缓存。相同文件的并发请求合并，缓存最多保留 128 项摘要，不保留整个文件内容。文件替换、修改、删除及 App 重启都会触发重新读取或原有错误处理。

### 跨浏览器配置初始化

从宿主当前共享对象读取 `statsig_evaluations`，通过原 SDK 的 `dataAdapter.setData` 和 `initializeSync` 接入。只有以下条件全部满足才使用：

- SDK key 和完整 SDK user 一致，包括账号、宿主设备 ID、语言、App 版本、会话、套餐及其他自定义属性。
- 数据包含完整配置结构，时间戳不在未来，且不超过 10 分钟。
- 原 SDK 没有禁用存储，客户端尚未初始化。

命中时第一轮渲染无需等待配置请求；原界面报告 `first_content_visible`、桥接真正完成后，再等待 1 秒调用 SDK 刷新。页面退出或启动失败会取消等待；身份改变时不刷新旧身份。若其他初始化长期未完成，30 秒后仍尝试验证配置。原 SDK 的自动刷新和实验值保持原语义，未强制开启任何 gate。未命中时走原异步初始化。

此前的 IndexedDB 缓存修复继续保留：最多 4 项、约 16 MiB；小键留在 localStorage，存储关闭时不打开数据库。

### 当前启动快照

每次 `/bridge/bootstrap` 请求通过常驻 relay 读取当前共享状态和侧栏信息。侧栏使用原版已有的同步 IPC 读取当前宿主缓存，绕过 preload 的永久缓存。并发请求合并；超时或宿主失效返回未就绪，不把旧快照当作新结果。这里读取的是现有状态，不重建 AppHost。

### 网页上报与传输

浏览器的 `startup.isSentryEnabled` 返回 false，避免使用不存在的 Electron IPC 上报通道；原生宿主自己的上报不受此适配器控制。没有全局屏蔽控制台错误。

此前的二进制 Base64 桥接继续保留，避免把字节展开成巨大 JSON 数字数组；仍兼容旧协议和流式 HTTP 转发。

## 完整页面对比

App 版本为 26.1007.21434。同一台 ARM 机器上分别启动独立宿主与独立 Electron/Chromium 浏览器，HTTP/WS 走回环地址。每组重新启动宿主、清空临时浏览器 profile；依次首次打开、同一浏览器再次打开、全新浏览器。比较组已包含上一轮 Base64 与 IndexedDB 修复。

以下为最后一组**关闭 CPU profiler**的测量，取原版界面的 `first_content_visible` 对应完成时间，不取服务握手时间，也没有提前隐藏加载提示。

| 场景 | 本轮修改前 | 本轮修改后 |
| --- | ---: | ---: |
| 首次打开 | 24.0 秒 | 24.2 秒 |
| 同一浏览器再次打开 | 23.4 秒 | 21.5 秒 |
| 全新浏览器 | 20.5 秒 | 19.6 秒 |

修改后的第二、三次均观察到 `config-cache-hit`，进入 Statsig provider 时已完成初始化；运行时摘要函数的文件读取量均为 0。首次建立缓存仍需要实际校验文件。网页的 `sentry-ipc://` 失败记录为 0，配置配额错误为 0。

这是少量顺序样本，机器还有其他工作，测试浏览器也运行在同一台 ARM 机器上。结果不能外推为远程强性能浏览器的固定提速比例；首次打开没有改善，后续打开的完整首屏仍较慢。大文件读取减少是已经验证的宿主改善，不能据此声称全部等待已消失。

## 验证与使用

`npm test` 63 项、Python unittest 18 项通过。覆盖文件修改/替换/删除、并发校验、故障重试、缓存边界、完整配置身份匹配、过期和损坏数据、隐私设置、首屏后刷新和退出取消、当前快照读取、宿主断开与超时，以及既有流式 RPC、资源与文件操作行为。

对真实原包的选定函数做唯一匹配校验；官方 App 改动匹配结构时会停止准备并提示不兼容。代码只写入私有副本和浏览器静态资源，不改官方安装包。未做 Docker 测试。

诊断记录保存在 `.logs/startup-investigation/unprofiled-before/`、`unprofiled-after/` 和此前的采样目录。原始日志可能包含个人信息，不应直接公开。

按原命令重启宿主一次即可应用代码和新的静态资源版本。摘要缓存持续到宿主退出；同一身份的新浏览器可复用新鲜配置。宿主刚启动、配置过期、身份或语言改变等场景仍需正常初始化。
